**Prompt:** 现在 name 怎么存在 presence 里的？合理吗，我以为会有一个单独的 user profile 表呢。presence 不应该单独只用于位置共享吗？

**Model:** Claude Opus 5 via Claude Code

**What was done:** Added `users/{uid}` as the durable source of truth for public player profiles, after the review above found that `presence` was the only collection other clients could read a name from — and `presenceRepository.removePresence` deletes that document whenever a player stops sharing location. This blocks roadmap item 11 (Leaderboard), which needs uid→name for offline players.

- `firestore.rules`: new `users/{uid}` block — readable by any signed-in player, writable only by the owner, field whitelist (`displayName`/`createdAt`/`updatedAt`), `createdAt` immutable on update, no deletes
- `src/features/backend/userProfileRepository.ts`: `getUserProfile` / `syncUserProfile`; the sync skips the write entirely when the stored name already matches, so launching the app costs no write
- `src/lib/auth.ts`: `registerUser` and `updateUsername` mirror the name through; `syncUserProfileFromAuth` backfills on sign-in, called from `useAuthUser`
- Tests: `userProfileRepository.test.ts`, `auth.test.ts` (28 tests total, all passing)
- `docs/product-design/Roadmap.md` item 11 annotated so the next person reads names from `users`, not `presence`

**Design decisions:**

- The `displayName` copy in `presence` is kept as a read cache — denormalizing it avoids an extra read per map pin, and the 60s heartbeat rewrites it from Auth, so it self-heals within one heartbeat.
- Auth `displayName` stays the source of truth; mirror writes are best-effort because the sign-in backfill is a real repair path.
- No email in `users` — the collection is readable by every signed-in player. The backfill reads `auth.currentUser.displayName` directly rather than the hook's fallback chain, which ends at the email address and would have published it.

**Not done (deferred):** `playerStatsRepository.getPlayerStats(uid, displayName)` keeps its caller-supplies-the-name signature (roadmap item 8 rewrites it anyway); no bulk profile query (item 11's call); QR payload and `challengeRequests` name copies left alone as point-in-time snapshots.

**Correction after checking the deployed rules:**

- Production already had a `users/{uid}` block, added by a teammate, with the same rationale in its comment but a narrower shape — `hasOnly(['displayName'])`, no timestamps. The repo's `firestore.rules` had drifted from production.
- Adopted the deployed shape rather than publishing ours: the `createdAt`/`updatedAt` fields we had added were speculative (nothing reads them) and changing a live contract for them was not worth it.
- `syncUserProfile` now writes `{ displayName }` only, and `firestore.rules` in the repo is byte-identical to production — **no rules deploy needed**.

**Still open (pre-existing, not from this change):** `challengeRequests` has no security rule in either the repo or production, so `challengeRequestRepository.sendChallenge` writes are denied by Firestore's default-deny. Already noted in the architecture report.
